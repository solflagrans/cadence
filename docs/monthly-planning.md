# Приоритеты и месячные планы

## Модель первого этапа

**Приоритет** существует независимо от месяца. Поля: идентификатор, владелец,
название, метрика (`time`, `quantity`, `volume`), единица для количества и объёма,
признак архива. Названия в интерфейсе: «Время», «Количество», «Объём».
Название — 1–120 символов после удаления внешних пробелов; единица — 1–32.
Названия не уникальны: совпадение текста не означает совпадение приоритетов.

**Месячный план** связывает приоритет с месяцем `YYYY-MM` и положительным объёмом.
Поля: идентификатор, владелец, приоритет, месяц, объём. Один приоритет может иметь
не более одного плана на месяц. Отсутствие записи означает отсутствие плана;
нулевой объём не используется как скрытое удаление.

Время — целые минуты (от 1 до 2 147 483 647, предел PostgreSQL integer).
Количество — положительное целое число до 2 147 483 647 (занятия, страницы);
дробные значения отклоняются без округления. В предметном слое это number.
Объём — точное десятичное значение до 9 знаков в целой части и 3 в дробной
(PostgreSQL numeric с CHECK на диапазон и точность, без автоматического
округления при записи). В предметном слое объём передаётся
строкой: `12,500` нормализуется в `12.5`. Двоичная арифметика с float не нужна.
Объём допускает также значения без дробной части: `12` км. Единица сама по себе
не определяет метрику — тип явно выбирается при создании приоритета.
Лимиты хранения не являются рекомендацией по реалистичному объёму плана.

Метрика и единица принадлежат приоритету и после создания неизменяемы.
Для перехода от страниц к книгам создаётся новый приоритет. Название можно менять;
переименование применяется во всех месяцах. Истории названий в MVP нет.

Объём меняется только в выбранном месяце, включая прошлые месяцы.
Это соответствует правилу расчёта прогресса относительно текущего плана.
Архивирование не удаляет и не изменяет планы: существующие планы редактируются,
новые добавляются после восстановления приоритета.

Удаление из месяца и архивирование — отдельные операции. Серверная
операция удаления плана допускается только при отсутствии связанных недельных
планов и фактических записей; иначе возвращается понятная ошибка. Каскадное
удаление результатов не допускается. Будущие таблицы недель и факта должны
ссылаться на план с ON DELETE RESTRICT.

## Календарь

Месяц — календарный ключ, а не timestamp. Текущий месяц будет определяться
по сохранённому часовому поясу пользователя. Его выбор не меняет правило
принадлежности недель: неделя относится к месяцу своего четверга.
В первом этапе месячный план не разбивается автоматически по неделям.

## Границы ответственности

- `src/modules/priorities/domain/priority.ts` — типы, проверки, создание,
  переименование, архивирование и восстановление приоритета.
- `src/modules/monthly-plans/domain/monthly-plan.ts` — месяц, объём,
  создание плана и изменение его цели с проверкой совместимости метрик и связей.
- Предметные функции не обращаются к БД, React, Auth или системному времени.
  Идентификаторы и владельца передаёт прикладной слой.
- Проверка соответствия владельцев в модели не заменяет авторизацию:
  будущий сервер получает пользователя из доверенного контекста и загружает
  только принадлежащие ему данные. Идентификатор владельца из формы не принимается.

## Реализовано: хранение и серверные операции

1. Таблицы приоритетов и месячных планов с явным `owner_id`. Дублирование владельца
   в плане защищается составным внешним ключом `(owner_id, priority_id, kind)`.
2. Ограничения БД для метрик, положительных объёмов, единиц и уникальности
   `(owner_id, priority_id, month)`. Совместимость метрики плана и приоритета
   также обеспечивается на уровне БД.
3. Создание приоритета вместе с первым планом — в одной транзакции.
   Повтор операции с тем же ключом возвращает прежний результат; повтор ключа
   с другим содержимым отклоняется. Уникальности названия для этого недостаточно.
4. Версия записи для защиты от потери изменений: устаревшая версия отклоняется,
   а форма сохраняет ввод и предлагает загрузить актуальные данные.
5. До подключения Auth разрабатывать операции с явным контекстом владельца
   и тестовыми данными; публичный доступ к пользовательской БД не открывать.

## Следующий шаг: интерфейс

Экран месяца: переключатель периода, список приоритетов с объёмами и кнопка
добавления. Форма позволяет создать приоритет вместе с планом либо выбрать
существующий активный приоритет, ещё не включённый в месяц.
Для времени — часы и минуты, для количества — целое число и единица,
для объёма — число с возможной дробной частью и единица.
При редактировании имени достаточно короткой пометки «Во всех месяцах».
Текст интерфейса следует правилам AGENTS.md: кратко, без служебных пояснений.
Прогресс появится вместе с записью факта; пока отображается только план.

Статус: предметный слой, хранение и внутренние серверные операции реализованы.
Следующий шаг — интерфейс. Визуальную проверку выполняет пользователь.

## Вызов серверных операций

`application/server.ts` открывает и освобождает подключение через `withDatabase`.
`createPlanningService(db)` содержит тот же сценарий с переданной БД для тестов.
Это внутренний серверный интерфейс, не публичный API. Перед публикацией маршрутов
владелец должен определяться из сессии, а не из формы или параметров запроса.

- `listMonth(ownerId, month)` возвращает пары приоритет/план выбранного месяца.
- `listPriorities(ownerId)` возвращает приоритеты владельца, включая архивные.
- `executePlanningOperation(ownerId, { operationId, command })` выполняет команду.
  `operationId` — UUID, неизменный при повторе одного запроса. Новое намерение
  требует нового ключа. Ответ на повтор — исходный результат; для актуального
  состояния после него можно перечитать месяц.
- Команды: `create`, `add`, `rename`, `archive` (также восстановление), `target`,
  `remove`. Изменение и удаление требуют `expectedVersion` из прочитанной записи.
- Ожидаемые ошибки имеют код: `invalid`, `not_found`, `conflict`, `duplicate`,
  `archived`, `metric_mismatch`, `operation_reused`, `has_dependencies`.
  Чужие и отсутствующие записи дают одинаковый `not_found`.
  Неожиданные ошибки БД передаются серверному обработчику и не должны попадать в UI.

## Проверки и миграция

`pnpm test` включает интеграционные тесты на PGlite с применением миграций Drizzle.
Проверяются откат транзакции, повтор запросов, версии, изоляция пользователей,
архивирование, удаление и ограничения БД. PGlite сериализует транзакции в одном
подключении: это не проверка блокировок отдельных соединений Neon или его транспорта.

`migrations/0000_monthly_planning.sql` подготовлена и проверена локально.
К облачной базе миграция в рамках этой задачи не применялась.
